**The pattern, sized off W&B:**

1. **Train pass@8 ordering (Minority > GRPO > Poly-EPO) is *inverted* on held-out AIME-25** (GRPO ≥ Poly-EPO ≫ Minority). The arm with the best in-distribution training signal is the worst on hard OOD — exactly the generalization-gap signature minority voting was supposed to *prevent*.
2. **Per-step advantage scale shrinks by ~2× from GRPO → Minority and ~7× from GRPO → Poly-EPO.** At the same nominal LR, set-arms see a much smaller effective gradient. This is not a bug (it's what the marginal-advantage averaging does to the variance), but it means LR=3e-6 is not actually matched.
3. **`fraction_filtered` divergence is dramatic** (53% GRPO vs 15–20% set arms). Set arms train on ~3× more prompts per step, but most of that extra signal is on prompts where GRPO would have correctly judged "no advantage to learn here." Suspect the set arms are spending gradient on low-information prompts.
4. **`distinct_clusters_mean ≈ 3.4 / 8`** on both CoT arms — judge is producing real cluster structure (not all-singleton, not all-one-cluster). **`degenerate_rollouts ≈ 250–280 / 1024`** (~25%) — non-trivial but not catastrophic.
5. **Step mismatch:** GRPO is ~110 steps ahead of the set arms (~149s/step vs ~205s/step — judge overhead). Step-matched comparison matters for any "final ckpt" claim.

## 3. Diagnostic evals — why didn't minority help?

These are the ones that earn the poster's "Analysis" half if Minority loses (which the snapshot suggests it will). Ordered by signal-per-hour; do at least 3.1–3.3 even if compute is tight.

### 3.1 Step-matched and reward-matched comparison (cheap, decisive)

GRPO has seen ~110 more steps' worth of prompts. Two controls:

- **Step-matched:** evaluate every arm's checkpoint at step 200 (the saved `global_step_200` ckpt on each volume) on the full panel. If Minority is *still* behind at the same step, the gap is not "GRPO ran longer."
- **Compute-matched:** GRPO at step 313, set arms at step 200 = roughly the same wall-clock and Modal $. This is the *fair* comparison for "what does a fixed budget buy you?" Report both.

Action: pin three ckpt paths per arm now — `step_50`, `step_200`, final. Don't lose mid-step ckpts.

### 3.2 Coverage and diversity at eval time (the actual minority hypothesis)

The whole point of minority voting is **broader coverage** of the answer space at high k, even at the cost of pass@1. Measure it directly:

- **Coverage@k:** number of *distinct correct* answer clusters discovered in k rollouts, averaged over problems. Compute on AIME-25/26 where there is one gold but many wrong-but-plausible answers, and on Polaris 2k.
- **Answer-cluster entropy@k:** entropy of the answer-hash distribution over k rollouts, per problem. Higher entropy ⇒ less mode-collapse.
- **CoT-cluster entropy@k:** run the production judge over k=8 eval rollouts (one judge call per problem on each arm), entropy of cluster ids. Only feasible on AIME-25/26/BeyondAIME because of judge cost.

**Predicted outcome if minority "works as designed":** Minority-CoT loses pass@1 but wins coverage@8 / entropy@8, especially on hard OOD. **If it loses on all three metrics**, the objective failed at its own goal — that's a real, publishable negative result with a clear mechanism.

### 3.3 Per-rollout JSONL replay (diagnostic gold mine)

Each arm wrote `/vol/per_rollout/<run_id>/step_<n>.jsonl` with `{global_step, prompt_id, rollout_idx, parsed_answer, reward, cluster_id, finish_reason, response_length}`. Download these *before* the volume is reclaimed.

Analyses (offline, fast):

1. **Minority-vs-correctness alignment.** For each step, fraction of prompts where the *minority cluster* is the *correct* cluster. If this is ≤ 1/N_clusters (chance), the objective is upweighting wrong answers as often as right ones — directly explains the AIME-25 collapse.
2. **All-wrong rare-reward signature.** Fraction of prompts where all 8 rollouts have reward=0 but the marginal advantage is non-zero for some rollout. This is the "reward the lone weird wrong CoT" failure mode the v2 memory flagged (`bin[0.0,0.0]` rising).
3. **Advantage-correctness correlation.** Per-prompt Pearson(A_i, r_i). For GRPO this is 1.0 by construction. For Minority it should be *positive but lower*; if it's near 0 or negative on a meaningful fraction, the objective is misaligned with reward.
4. **Length and finish-reason drift.** `response_length/mean` over training, split by reward. Minority's broader-coverage incentive could be encouraging longer, lower-quality rollouts (or shorter ones that just guess different answers).
5. **Per-difficulty-band pass rate trajectory.** Polaris has 8 difficulty bands. If Minority gains on easy bands and loses on hard bands, that's diagnostic. If the loss is uniform, it's a learning-rate / advantage-scale problem.

`main/scripts/analyze_aime_rollouts.py` is referenced in STATUS as the pattern to follow. Re-use it for 3.3.1 and 3.3.2.

### 3.4 Advantage-scale ablation (one extra short run if budget allows)

The ±0.125 advantage range on Poly-EPO at LR=3e-6 means effective LR is ~7× smaller than GRPO. To separate "objective is bad" from "objective is fine but underdosed":

- Take the current Poly-EPO ckpt at step 200, continue 50 steps at LR=2e-5 (≈7× scale-up). If it now matches GRPO trajectory, the answer is "Poly-EPO works but our LR sweep missed it."
- Same for Minority at LR=6e-6 (≈2× scale-up).

This is 1–2 hr of compute per arm, defensible as a poster ablation. Skip if the §3.1 step-matched eval already shows a clear separation that LR can't explain (e.g. Minority is *worse than base model* on AIME-25).

### 3.5 KL-from-base sanity check (cheap)

Sample 200 prompts from Polaris held-out. For each arm's final ckpt vs Qwen3-4B-Base, compute mean per-token KL on the generated sequences. Predictions:
- If Minority KL ≪ GRPO KL → Minority barely moved the model; effective-LR / advantage-scale story.
- If Minority KL ≈ GRPO KL but Minority is worse → the model *did* learn, it learned the wrong thing → objective story.

This disambiguates the §3.4 outcome without needing a continued-training run.

### 3.6 Temperature sweep at eval (only if time)

Run AIME-25 pass@k at temp ∈ {0.7, 1.0, 1.3}. Diversity-promoting objectives should *gain less* from higher temp (model is already diverse) and *lose less* at low temp (model has stable modes). If Minority's temp-curve looks the same as GRPO's, it's not actually inducing diversity.

- **No pass@64 / pass@128.** Diminishing returns vs. the AIME-30 problem count; the bootstrap CI eats any apparent signal.
