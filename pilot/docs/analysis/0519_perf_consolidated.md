## A. Contradictions / Open Questions

1. **Gradient checkpointing: ON or OFF for performance?**
  - `0519_perf_audit.md` §4 recommends turning it **off** for ~35–45% backward speedup, stating "80GB may allow checkpointing off."
  - `0519-12_grpo-oom-root-cause.md` §5.2.b recommends keeping it **on** as a memory safety measure to maintain 3–4× activation footprint reduction.
  - `MAIN_RUNS_PLAYBOOK.md` §1 pre-launch checklist explicitly instructs: "verify `policy.gradient_checkpointing_enable()` is still called."
  - These three documents were written by different agents. The perf audit optimizes for speed; the OOM analysis optimizes for memory headroom; the playbook assumes it stays on. No document reconciles them. **Resolution requires a smoke step at both settings with `nvidia-smi` peak VRAM monitoring.**
2. `**allow_seeded_prompt_batching` speedup estimate: ~4–6× (audit) vs qualitative "material" (playbook)**
  - `0519_perf_audit.md` §1 and §8 estimate **~4–6× decode speedup** → build ~26 min → ~4–7 min.
  - `MAIN_RUNS_PLAYBOOK.md` §1 describes the A100 as "~40% utilized during decode" and says enabling seeded batching should "materially raise" utilization but does not quantify the expected step-time change.
  - The 4–6× estimate is derived analytically (32 serial → 4 batched rounds × some GPU saturation gain); actual speedup depends on HF `generator=` list path efficiency. Not yet measured.
3. `**old_logprobs` reuse: safe or not?**
  - `0519-12_grpo-oom-root-cause.md` §5.2.d says reusing rollout logprobs for `old_logprobs` is "none" experiment impact "for pure on-policy GRPO with no PPO clipping across multiple epochs."
  - The code runs 1 inner epoch, so this should be safe. However, `output_scores=True` in HF `generate` returns token scores at a different numerical precision point than a separate `model(ids).logits` forward. The discrepancy is likely sub-noise but **no document verifies this claim numerically**.
4. `**kl_coef: 0` — perf win or experiment change?**
  - `0519-12_grpo-oom-root-cause.md` §5.3.a calls the KL term "sub-noise" at 0.001 and marks experiment impact as negligible.
  - No other document takes a position, and `shared_train.yaml` freezes `kl_coef: 0.001` as a shared hyperparameter across all four matrix runs. Setting it to 0 would require a labeled branch and should not be done silently.
5. **A100 utilization quoted as ~30% vs ~40%**
  - `0519-21_run0-silent-rollout-progress-investigation.md` and `pilot/docs/issue.md` report GPU utilization "~30%" during Run0 rollouts.
  - `MAIN_RUNS_PLAYBOOK.md` §1 states "~40% utilized" during pilot decode.
  - These may refer to different measurement windows or runs (Run0 at 1024 tokens vs GRPO at 2048 tokens). Neither is precisely defined.

## B. Buried Gems (findings not in `0519_perf_audit.md`)

1. **A100 ~40% utilized during decode — confirmed mechanism in `MAIN_RUNS_PLAYBOOK.md`** (not in perf audit). The playbook identifies the exact cause: `allow_seeded_prompt_batching=false` is the default **and** is explicitly set in `run0_proxy.yaml:12` and `run3_f_grpo.yaml:8`. The other GRPO run configs (`run1_grpo.yaml`, `run1b_grpo.yaml`, `run2_inverse_freq.yaml`) do not set it, so they also fall through to the serial path. **No run in the current pilot matrix uses batched decode.** The perf audit notes the default is false but does not enumerate which configs have it explicit.
2. `**execute.py` hard-caps `max_new_tokens` at 1024** for Run0 and tier-1 eval (`execute.py:63,152`), while GRPO training uses 2048 from the config. This creates a **silent behavioral asymmetry between training and evaluation** not mentioned anywhere in the perf audit or incident docs. The policy is trained at 2048-token horizon but evaluated at 1024. If intentional for memory management, it should be documented. If accidental, it understates eval performance.
3. **Duplicate `policy.save_pretrained()` call** in `run_grpo_training` (`hf_grpo_train.py:962-966` and `991-996`). Both calls save to the same `out_dir / "checkpoint"`. The second save at line 991 is dead code — the checkpoint was already written and the `HFRolloutEngine` already loaded from it. This wastes ~10–20 s at end of every training run (serializing 3.4 GB bf16 twice to the same path). Not mentioned anywhere in docs.
4. `**HFPolicyModel` class and `_differentiable_loss` function are dead code** in the active training path. `run_grpo_training` calls `_train_step_microbatch_backward` at line 926. The `HFPolicyModel.logprobs_for_rollouts` method (the old accumulate-all-then-backward path from the OOM bug) and `_differentiable_loss` remain in the file but are unreachable. Dead code is a maintenance liability — a future refactor could accidentally restore the old path.
5. `**@modal.exit` hook is unused** (`0519-24_modal-observability-budget-gaps.md` §4). Modal provides ~30 s grace on preemption. Adding a `@app.cls` exit handler with `artifacts_volume.commit()` would allow partial state to be flushed before the worker dies. This was identified as "optional" in `0519-24` but not in the perf audit. The cost of not having it is quantified: ~$4+/lost step on `run1_grpo` preemption (`0519-14`).
6. `**budget_cap_gpu_hours` in YAML is not enforced in Python** (`0519-24_modal-observability-budget-gaps.md`; `0519-13_progress-log-milestone-misfire.md`). `run1_grpo.yaml` sets `budget_cap_gpu_hours: 12.0` — this field is never read by `execute.py` or the trainers. Only `budget_cap_usd` is enforced (between GRPO steps). The GPU-hours cap creates false confidence in budget control and could allow a stuck or runaway job to burn arbitrarily.
7. `**_build_step_groups` calls `_batched_scalar_mean_completion_logprobs` twice** — once for `old_logprobs` (policy forward, `hf_grpo_train.py:669-676`) and once for `ref_logprobs` (ref model, lines 677-684) — over the same 256 completions. This is 2× the irreducible no-grad forward cost. The `0519-12` OOM doc notes `old_logprobs` can be eliminated via `output_scores=True` for on-policy GRPO; the perf audit notes it but doesn't quantify the build-phase contribution separately from rollout. Actual cost: ~250 forward passes in the build phase, ~half of build time is policy+ref logprob computation vs rollouts.
8. **Debug scaling from `run1b` logs gives a concrete rollout-dominance estimate** that the perf audit references but incident docs put the raw numbers: 8 prompts × 512 tokens → 145s build; extrapolating to 32 × 2048 gives ~~2320s vs measured ~1500s. The discrepancy (~~35% faster than linear) suggests partial GPU saturation even in the serial path at larger shapes. This means the batching speedup may be lower than the 4–6× analytical estimate.
